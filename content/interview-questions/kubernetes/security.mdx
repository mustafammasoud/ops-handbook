<InterviewQuestion
  id="k8s-rbac-role-vs-clusterrole"
  number={1}
  difficulty="intermediate"
  tags={["kubernetes", "security", "rbac"]}
  question="ما الفرق بين Role و ClusterRole، ومتى نستخدم RoleBinding مقابل ClusterRoleBinding؟"
  directAnswer="الـ Role يحدد صلاحيات محصورة داخل Namespace واحد فقط (مثل قراءة الكبسولات في مساحة dev). الـ ClusterRole يحدد صلاحيات على مستوى كامل الكتلة (Cluster-scoped مثل العقد PVs والـ Namespaces) أو صلاحيات لجميع مساحات الأسماء معًا. عند استخدام RoleBinding مع ClusterRole، يتم تقييد تلك الصلاحيات لتنطبق فقط داخل مساحة الأسماء التي أُنشئ فيها الـ RoleBinding."
  pitfalls={[
    "منح حساب خدمة (ServiceAccount) صلاحية ClusterRoleBinding مع امتياز cluster-admin كحل سريع لتفادي أخطاء الصلاحيات، وهو خرق أمني جسيم في بيئات الإنتاج.",
    "الاعتقاد بأن ClusterRole يتطلب دائمًا ClusterRoleBinding؛ استخدام RoleBinding لربط ClusterRole قياسي (مثل edit أو view) هو أفضل ممارسة لتقييد الصلاحية في Namespace محدد دون تكرار إنشاء Roles."
  ]}
  followUps={[
    "ما هي الحقول الأساسية في قاعدة RBAC (apiGroups, resources, verbs)؟",
    "كيف يمكنك التحقق مما إذا كان المستخدم أو الحساب يملك صلاحية معينة باستخدام أمر kubectl auth can-i؟"
  ]}
>
المصفوفة الكاملة لعلاقات الـ RBAC:

- **Role:** صلاحيات داخل مساحة أسماء محددة.
- **ClusterRole:** صلاحيات عامة لكامل الكتلة أو كائنات غير مقيدة بـ Namespace (كالعقد Nodes و PersistentVolumes).
- **RoleBinding:** يمنح الصلاحيات داخل مساحة الأسماء الخاصة به فقط.
- **ClusterRoleBinding:** يمنح الصلاحيات على مستوى كامل الكتلة لكل مساحات الأسماء والموارد العامة.

**مثال تطبيقي احترافي:**
إذا أردت منح مطور صلاحية `view` في مساحة `staging` فقط دون منحه صلاحية على الكتلة بالكامل:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-view
  namespace: staging
subjects:
- kind: User
  name: ali@example.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole   # استخدام ClusterRole العام الجاهز
  name: view
  apiGroup: rbac.authorization.k8s.io
```

<InterviewQuestion
  id="k8s-security-context-hardening"
  number={2}
  difficulty="advanced"
  tags={["kubernetes", "security", "security-context", "hardening"]}
  question="ما هي الإعدادات الإلزامية في SecurityContext لتحصين الحاوية (Hardening) ضد ثغرات الهروب من الحاويات (Container Escape)؟"
  directAnswer="تشمل الإعدادات الأساسية: runAsNonRoot: true لمنع التشغيل بصلاحية المستخدم الجذر root، readOnlyRootFilesystem: true لمنع المهاجم من تعديل ملفات النظام التنفيذية أو تنزيل برمجيات خبيثة، allowPrivilegeEscalation: false لمنع اكتساب صلاحيات إضافية عبر suid binaries، وإسقاط جميع إمكانيات لينكس عبر capabilities.drop: ['ALL']."
  pitfalls={[
    "تفعيل privileged: true داخل بيئات الإنتاج، مما يمنح الحاوية إمكانية الوصول المباشر لكافة أجهزة وعمليات الخادم المضيف ويجعل الهروب من الحاوية أمرًا شبه مؤكد عند اختراق التطبيق.",
    "تفعيل readOnlyRootFilesystem دون توفير emptyDir volumes للمجلدات المؤقتة التي يتطلبها التطبيق للكتابة (مثل /tmp أو /var/run/app)."
  ]}
  followUps={[
    "ما الفرق بين SecurityContext على مستوى الـ Pod (pod.spec.securityContext) وعلى مستوى الحاوية (pod.spec.containers[].securityContext)؟",
    "ما هي معايير Pod Security Standards الثلاثة (Privileged, Baseline, Restricted)؟"
  ]}
>
نموذج SecurityContext محصن للإنتاج وفق معيار **Restricted Pod Security Standard**:

```yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: secure-app
    image: my-app:v1.0.0
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop:
        - ALL
    volumeMounts:
    - name: tmp-dir
      mountPath: /tmp
  volumes:
  - name: tmp-dir
    emptyDir: {}
```
هذا التكوين يمنع:
- تعديل أي ملف في نظام الملفات.
- استغلال برامج SUID للحصول على صلاحيات إضافية.
- استخدام أي إمكانيات خاصة بنواة لينكس مثل `CAP_NET_RAW` أو `CAP_SYS_ADMIN`.
</InterviewQuestion>
